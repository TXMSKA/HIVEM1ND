# Changelog

## Unreleased

- The Overlord leads a squad as a mini manager. Its scope is an environment, working exactly as before, or the chats of one repository, in which case it plans the request, splits it into tasks for its members, hands each one its task by the member's `job` when it has one, reviews each delivery first-hand and either approves it for the person with one line in the task's Report, `Approved for review by <unit> on <date>`, or sends it back to `open` with what is missing written in the Report, passes the person's decisions to its members and reports to the coordinator with the `User decisions` notes. The unit is `overlord-<environment>` or `overlord-<project>`. The state format gains two optional headers: `lead: <unit>`, the unit a member reports to, and `job:`, what the unit always does, such as `reader`, `archiver`, `builder`, `reviewer` or a short description. A squad is a lead plus every unit whose state names it, the unit name, its job and the model as the session records it live in the state so a host can create a chat by writing them, nothing ties a member to one tier, and a person's review of a task whose executor has a lead waits for the approval line, with no new status. A unit with no `lead` works as it did. An Executor with a lead takes its tasks from it, reports each delivery with a Relay message, copies the lead when the person messages it directly with something that changes the plan and keeps to its job. The Manager talks to the lead, not to each member, unless the person addresses a member; `/plan` sends a task for such an executor to its lead, and `/qa` leaves the approval to the lead.
- The model table: `models.md` is a new record in `files.md` that says which model does which kind of work, at which effort, for every seat and every delegation. It has one row per kind of work and client with Work, Client, Model, Effort, Status (`active`, `paused` or `candidate`), Tested and Result, then a fallback order; a row changes only when a test changes it, a tool moves from `candidate` to `active` only after a real test (for another client, a Relay live trial), a tool that stops being available is `paused` and keeps its history, and prices stay out. The kit speaks in tiers, in a `delegation` knowledge category: plan, scope, product document and deep review at strong and max, seat work at strong and high and never delegated, builds from an approved plan at mid and high, read-only gathering at light and low, mechanical edits at mid and low; the seat verifies every delegated result and builders run their own tests. The Adapters section of Genesis maps the tiers to the model families of each client, and setup writes the first file from that mapping. The Executor takes the row of each piece, the Manager names a row's model and effort when it briefs, a task may carry a `work` header, and `/qa` runs its subagents on the build row. The startup `check` prints one line for a row whose Client is neither a Relay wake adapter key nor `subagent`, naming its Work and the client; valid rows, a missing file and a file without a table stay silent, `--json` carries the findings under `mind.models`, and the measurement never fails the check.
- Product documents: every project has one, `projects/<project>/product.md`, a new record in `files.md` with a header (project, family, stage, updated, voice, board) and the sections Problem and audience, Value, Requirements per stage with an ID such as `APP-B-04` and an acceptance criterion each, Out of scope, Plans, Floors, Depends on, Open questions and Annexes. An annex, such as the architecture, holds the how in `projects/<project>/annexes/<name>.md`, or a repository path when it already lives there, and cites requirement IDs instead of restating them. The family product document holds the price table once and adds Rules, Product map, Stages and a pointer to the design direction. A brief Fact that changes a product document carries a `(product: <section>)` pointer and shrinks to one line, a task may list the requirement IDs it delivers in a `requirements` header, and one home per fact says which file owns each kind of fact.
- `product`, a knowledge module with the `product-requirements` protocol, run through `/protocol`: it gathers the brief, the scope and brainstorm records, the boards, the task Architecture sections and the voice specification, writes the product document with its requirements, out-of-scope list, open questions and annexes, and cross-checks it against the brief, the boards and the voice. `/brainstorm` stays the drafting tool, and there is no `/product` command.
- The startup `check` prints one line for a product document older than the newest brief Fact that carries a `product:` pointer, naming the project and the Fact date; a Fact without a pointer never triggers it. A project with a brief and no `product.md` is reported too: one line naming the project when the working directory resolves to it, and at the mind root one line with the count, none at zero. `--json` carries the list under `mind.product.missing`. A product document over 20 KB (`productBytes`) is listed with the other sizes, and `--json` carries the product document sizes and findings. The measurement never fails the check, and `/cleaner` lists product documents among what it measures.
- The seat of each project, its Executor, writes and keeps the project's product document: at the start of its session, when the project has a brief and none, it writes it from the records through the `product-requirements` protocol before other work, and afterwards it edits it in the turn a product decision is taken, sending the coordinator its `User decisions` note. The coordinator, the Manager or the Overlord when the mind has none, reviews each product document against the user's decisions and approves it with the user, drafts one only for a project with no seat and owns the family product document. A decision taken with the coordinator reaches the seat as a brief Fact with its pointer and a `Product decision` Relay note, and the check reports the gap until the seat edits the document. The Incubator hands an accepted idea to the seat of its project, or to the coordinator when the project has none. A change to a product document that touches a shared contract sends one Relay note to each product listed in Depends on. `/plan` writes tasks that cite requirement IDs, and `/qa` reports the requirements met against the total per stage.
- The Relay host client is now `host`: `relay wake attach --client host`, the MCP `client` value and the wake adapter label use it, with no alias for the earlier id, and the Relay setup text, the files examples and the fixtures use generic host, machine and project names.
- An install or an update compares text without regard to line endings, because machines that share a mind may check the kit out with different ones. A kit file that already holds the same text under the other ending is left as it is and recorded as it is on disk, a recorded hash matches the file under either ending, and binary content is still compared byte for byte. A kit file that matches the record of another machine of the same mind (`machines/<host>.managed.json`) is managed and is updated or removed without a conflict, where it was reported as unowned or modified; a file that matches no record still asks for a choice, and a piece of the user's own in `roles/`, `features/`, `commands/` or `knowledge/` is still kept with a warning.
- `evolve` asks for conflict choices only in a terminal. Without one, it prints each unresolved conflict with its allowed choices and the `--conflict <path>=<choice>` syntax, never waits for an answer and exits with code 1.
- `/evolve` passes `--json` on every run and reads the conflicts from it. A mind that is not a Git checkout and is on a prerelease line (`user/VERSION` with a hyphen, such as `2.0.0-experimental.3`) no longer takes the published package as its base: the command uses a local clone of the kit repository on the branch of that line, fast-forwarded first, as `--kit-path`, and stops naming the clone it needs when the machine has none.
- The Antigravity allow rules that `relay configure --client antigravity` writes end in a token that refuses shell control characters (`;`, `&`, `|`, `<`, `>`, `(`, `)`, `$`, the backtick, `{`, `}` and line breaks) instead of a wildcard, so a chained, substituted or redirected command no longer passes when Antigravity matches the whole line; running `configure` again replaces the earlier rules, and `relay unconfigure --client antigravity` removes both forms.
- The Antigravity CLI wake lets a woken turn run to its result within 120 seconds (the controller bound moves to 125 seconds and the lease to 180 seconds, and the controller's retry-policy limits rise to 180 and 300 seconds), and `relay configure --client antigravity` adds a reversible allow rule in `~/.gemini/antigravity-cli/settings.json` for only the kit's `relay read` and `relay send` commands on one mind, which `relay unconfigure --client antigravity` removes.
- `/cleaner`, a feature that keeps a mind lean: it measures preferences, briefs, stale states, read messages, Relay history, evidence folders, machine files and the repos of the machine's paths, proposes every change in one list for a single yes, applies it with the replaced text kept in a log entry, and runs the check again to verify. The startup `check` prints one extra line, and adds the measurements to `--json`, when a threshold is crossed (preferences over 20 KB, a brief over 15 KB, a state left `in` for more than 3 days, more than 500 MB of files that are not records, a machine file over 15 KB, more than 1000 Relay history files); the walk over the files is capped and the measurement never fails the check.
- The files a machine installed move out of its machine file into `machines/<host>.managed.json`, the same path-to-hash map. Setup, attach and evolve read the old `## Managed Files` section while the JSON file does not exist, and the next write migrates it, so the machine file keeps only its header, Agents, Paths and Excluded. An `evidence` entry in Paths survives a new setup.
- Launch checklists digested into the packs: the security module gains `personal-data`, a protocol for consent, third-party scripts, deletion and export, marketing mail and the privacy, cookie, terms and refund pages, with a data subsection and a pre-launch item; the design pack gains honest choices (unticked consent, an equal decline, real urgency, the full price), checks for the on-screen keyboard, Back and reload, raw error text, image alternatives and font and image licences; the copy pack gains rules for hidden fees, reviews, compliance claims, footer notices and unsubscribe links.
- `/absorb` and every role keep orders tied to the moment (which tool, model, effort or quota to use now) out of preferences, and a new preference replaces the line it contradicts in place.
- Relay supports GitHub Copilot: `relay configure --client copilot` writes the user `mcp-config.json` that the Copilot CLI and VS Code Copilot both read, and a `copilot` wake adapter resumes an exact existing CLI session through its ACP server with the same bounds as the other adapters (exact session load, no session creation, permissions never approved, pointer-only text, environment allowlist, no replay of an uncertain dispatch). VS Code wake and Copilot hooks are not covered; see the Relay setup feature for the undocumented contracts that await a live trial.
- `device-reach`, a design protocol that checks the approved default on simulated low-end phones, computers, Linux, other browser engines and the product's own app against performance budgets, with evidence or a named gap per profile; `/qa` offers it, with the user's yes, for tasks in its scope.
- Same-day awareness: every seat sends the coordinator (the Manager, or the environment's Overlord) one Relay note right after recording a user decision, correction or approval.
- Section tours: the design and copy packs teach each section on first opening with three or four key things and a More control that continues the tour.
- Executor, Incubator and Overlord fetch and fast-forward their repo before any work, not only at relay entry.
- Manager, an executive role that manages the whole mind: it surveys every project, defines scope with the user one topic at a time, gates the work before it reaches the executors and keeps its memory in `user/manager/`.
- `evolve` runs when started from a linked install inside the mind folder, and installs the roles, commands and features of the mind's `user/` folder when the kit and the mind are the same folder.
- Blueprint Lite routes links round the screens on separate tracks, so a line never crosses a screen or its title.
- The security module audits the full dependency tree at every severity and compares the count with the hosting platform's scan.

## 1.3.0 - 2026-10-02

- Four roles instead of eleven. Overseer, Technician, Super executor, Consultant, Executive, Operator and Marketing leave the kit: the Executor covers the single-repo seats and the Overlord the cross-repo work.
- Incubator, a new operative role that develops ideas into products inside one folder: it brainstorms an idea until it is well formed, analyses its opportunities and weaknesses, sends it to the product it belongs in or prototypes it fast, writes code with YAGNI first, and offers improvements to the product after doing what was asked.
- The Executor implements the plan itself by default and delegates to subagents or to another agent's command-line interface only when the user or a preference asks. It reads each request as plan mode (design, brainstorm, scope, no code) or operate mode (changes, fixes, reviews), and keeps the project's stage (Pre-Production, Production, Post-Production) and an internal version in the brief.
- An install or an update removes the files an earlier run wrote that the kit no longer ships, such as the skills of a removed role, keeping and reporting any file modified since.
- Void, the `/void` feature: a local reader on port 3301 that shows a JSON document one entry per page, both languages stacked on a black ground, and saves each correction into the file as plain text. The first save keeps the original as `<name>.orig.json`, every save is logged in `<name>.versions.jsonl` and raises the document's `rev`, and a document written from an older copy gets the lost saves applied again. Documents open from any folder, `--lan` serves a phone on the same network behind a key, and `widget.html` gives agents a read-only view inside the chat.
- Blueprint Lite opens to a phone on the same network: started with `--lan`, its server also answers on the machine's network addresses and prints a link with a key, which the phone keeps as a cookie; without the key those addresses refuse every request. A link that names only a project opens its first board.
- Blueprint Lite picks the project and the board from one button, so the top bar stays as long as its content however many projects there are. Its panel opens with a search, then the boards starred and the ones opened most in this browser, then every project folded to its name, the open one unfolded; each of them folds and unfolds. On a phone the tools bar is centred and as long as its tools, and the board note opens as a bubble out of a Note button in the tools bar, or with N, instead of folding from its title. The close button of a comment card and its Cancel work again, and a sent reply leaves its box empty on a phone.
- The design pack stops its fixes from spoiling an approved design. Each floor applies as its standard writes it: non-text contrast covers the boundary of a control with no fill of its own, not every button border, and the 16 px input size is for phones and touch. Every floor carries a soft option used first, a fix that changes anything visible is shown beside the board before it ships, behaviour notes stay off the design, every native select is opened and checked, and visual critique becomes a gate with a side-by-side against the board, a proportion check and a required fresh-eyes verdict.
- The design pack designs light themes instead of inverting dark ones: a `light-themes.md` topic and a `light-theme` protocol that read the source palette by the job of each colour, pick a dim, soft, standard or crisp contrast character, tint an off-white ground toward the neutral hue, keep white for raised layers outside the dim character, give each accent a text, a fill and a tint value at the lightness its floor needs, keep saturated colour to small areas, and judge both themes side by side. A light theme subcategory joins foundations.
- Switching machines takes one command on each side. The exit of `/relay` commits and pushes everything uncommitted in the repos of the unit's scope, on a new branch when the changes sit on the default branch, writes a state that resumes on another machine with nothing else, and clears the conversation; running it is the yes for those commits and pushes. The entry fetches, brings each repo to the branch recorded on exit and fast-forwards it, stopping only on uncommitted changes or a branch that cannot fast-forward, and asks for the yes to continue the half-done work. The scope is the current repo for a role in one repo, the environment for the Overlord and every project for the Overseer; a unit with several repos records each one in a `## Repos` section of its state.
- Present plays a Blueprint Lite board as a prototype: one screen at a time, fitted to the window, where a click on a control a link leaves from opens the screen it leads to. A click that misses lights the controls that lead somewhere, Back and Backspace return to the previous screen, and Escape goes back to the board.
- A Blueprint Lite screen can carry its own `note`. A click on the screen shows it in the note over the canvas, and a click on the empty canvas brings the board's note back.
- Blueprint Lite kit extension points: a repository adds its own icons (`docs/flows/kit/extra-icons.mjs`) and node types (`docs/flows/kit/extra-nodes.mjs`, measure and draw) over the shared kit without keeping a copy of `kit.mjs`.
- Blueprint Lite, the `/blueprint` feature: one local server per machine, on port 3300, draws the screen-flow boards of every project at once. Projects come from the mind (the machine record's paths and the routes), a project shows in the viewer when its repository has `docs/flows/boards/index.json`, and the comments made in the viewer are written to that repository's `docs/flows/comments/<board>.json`, where agents read them. The board and comment formats are documented in the feature. It ships as a folder with its scripts, and it is a temporary tool that the full Blueprint replaces. The shared kit measures text in the faces and weights of the skin it is drawn in, and follows the repository engines for three-value padding, stretched fixed-size children and dialog shadows, so a repository can drop its own `kit.mjs`.
- A feature folder is listed by its category in the content step of the installer, the same as a feature file.
- Tasks gain a `review` status between `open` and `done`: the executor sets it when it appends the report, the requester sets `done` on accepting the work and `closed` on archiving it. The swarm command counts tasks in review.
- The entry report of every role and of the relay command is laid out one block per fact, each led by a contextual icon, with the findings of the check first.
- Every role works without progress updates and reports once, when the work is done, with what was done and what is pending.

## 1.2.0 - 2026-09-21

- An install is never reported as done over files it did not write: a symbolic link or a Windows junction standing where files belong stops the run and asks, replacing the link by default and keeping the folder it points at, with omitting available as an explicit choice.
- Every install, attach and update writes `user/machines/<host>.report.md` with what it wrote, omitted or replaced.
- Attaching a machine is its own flow: a mind already installed is detected, simple mode attaches to it and custom mode asks at the mind location step, leaving the mind's content, preferences and version untouched.
- Roles, commands and features in `user/roles`, `user/commands` and `user/features` install like the ones the kit ships, so a role private to one mind stays out of the published folder.

## 1.1.1 - 2026-09-18

- OpenCode and VS Code attach in auto mode without manual steps: the rules line goes into the OpenCode global rules file and into a VS Code user instructions file.
- The attach prompt names the literal mind placeholder to replace instead of the mind path.
- Executor, Super executor and the plan command read the knowledge modules while planning, and write the build rules of the categories a task touches into the task as requirements.
- Protocols are a confirmation instead of a silent run: planning lists the ones whose scope matches the work, and each runs before the report only with the user's yes. The protocol command also lists the protocols of the knowledge modules.
- Executor delegates the implementation by default: the plan is split into pieces that share no file, each sent to a subagent on the next cheaper model and reviewed against the plan, with small pieces grouped into one brief. Pieces run one after another on the task branch, and only parallel pieces get their own worktree. A single concrete change, or the user saying so, is implemented directly. Super executor follows the same method.
- Local protocols per project in `user/projects/<project>/protocols/`, used only while that project is the current one, next to the global ones in `user/protocols/`.

## 1.1.0 - 2026-09-17

- Three chat roles that work from the mind alone, without a shell or a repository: executive decisions, technical direction and marketing.
- Security, design and copy knowledge modules, each with the command it installs: a security audit, a design and interface pass, and a rewrite of copy that reads as written by an AI, whole or scoped to one feature.
- Knowledge modules with an index of their protocols, so an agent loads the ones the work needs instead of the module.
- Protocols that run by themselves when a task is closed, matched against the work by their scope.
- Migration command, absorbing the rules, memories and notes an agent or a repository already holds, and leaving every original untouched.
- Roles, commands and features written inside the mind installed for every attached agent.
