# Changelog

## Unreleased

- The Cursor CLI wake resumes the conversation in print mode instead of through ACP. `agent acp` answered `Session not found` to `session/load` for every conversation created in the CLI, so the wake could never reach a real conversation. The worker now runs `agent --resume <conversation-id> -p --output-format stream-json --approve-mcps <pointer>` in the project directory of that conversation, never with `--trust`, `--force` or `--yolo`, counts the wake as submitted when the stream echoes the pointer as a `user` event of that conversation, and leaves the turn to run to its end. The start event took 13 to 21 seconds on Windows, so the adapter waits up to 60 seconds and the controller up to 65. An exit before the event is not submitted and says why (`cursor_workspace_not_trusted` when the CLI refuses an untrusted directory, `cursor_agent_exited`, `cursor_stream_malformed`, `cursor_session_mismatch`, `cursor_agent_error`), and a timeout is ambiguous and stops only that child. `--resume` creates a conversation for an ID it does not know, so the worker first finds the conversation under `%USERPROFILE%\.cursor\chats` and ends with `cursor_chat_not_found` instead of opening an empty one. A chat runs one resumed turn at a time: a pointer that arrives meanwhile is deferred without spending the retry or the handoff budget and is offered again after the turn ends. On Windows the worker still runs the bundled `node.exe` on the `index.js` of the newest CLI version under `%LOCALAPPDATA%\cursor-agent`, with `RELAY_CURSOR_AGENT` still winning. The editor is still woken only by the stop hook.
- A Cursor chat attaches itself with one command from inside its CLI shell and no environment variable: `relay wake attach --client cursor --unit <unit>` takes the native session ID from `CURSOR_CONVERSATION_ID` when `--native-session-id` is not given, and the wake reads the project directory from the `meta.json` of the conversation, so `RELAY_CURSOR_CWD` is only an optional override. The wake child keeps `APPDATA`, `ProgramFiles`, `ComSpec` and `USERNAME` beside the variables every client keeps, which the CLI and the MCP servers it starts need on Windows.
- Registering a chat again as the same unit reuses its record instead of writing a new one, and the Cursor stop follow-up finds a consent by unit and native session ID instead of by the ID of the record. Every new Relay MCP process of a Cursor chat registers again, and each registration made the wake policy name an old record, so the stop follow-up returned nothing and said nothing. A registration that carries an activity or a quota, or that changes the unit, still writes a record.
- The `sessionStart` hook of Cursor starts the worker of an enabled consent through the worker lease, so a chat no longer waits for a person to start it. `relay diagnose` lists under a client each consent that no worker serves as `enabled, no worker`, and `relay diagnose --client <client>` shows one client.
- Install and update bring the Relay-owned hook entries of a client that already has the Relay entry up to date in place: the command, timeout and loop limit of Cursor, the command of Codex, and the command and arguments of Claude Code. They report it as `hooks brought up to date` and ask for a restart. A foreign entry, and an event whose Relay entry a person removed, stay as they are, so a Cursor `hooks.json` written by an earlier kit no longer keeps its timeout of 5 seconds.
- `relay diagnose` lists, for Cursor, the `beforeShellExecution` and `preToolUse` hooks that Relay did not write, found in `~/.cursor/hooks.json` and in `~/.cursor/plugins/cache/**/hooks/hooks.json`, and warns when the manifest of a plugin that declares one says it is not supported on the current platform, since such a hook can reject every shell call.
- The Cursor rule `hivem1nd.mdc` carries a short contract for a woken turn: when Relay answers `NOT_REGISTERED`, register with the `CURSOR_CONVERSATION_ID` of the chat and the unit named in the pointer, read the inbox, act only on a hand-off and reply. Skills stay in `~/.agents/skills`, since the Cursor docs list it beside `~/.cursor/skills` as a user skills folder and the CLI reads both.
- On Windows the machine-local wake leases and locks move from `%LOCALAPPDATA%\hivem1nd\relay` to `%USERPROFILE%\.hivem1nd-relay`, because the Codex desktop app, a packaged app, redirects writes under AppData into its own package folder: its worker failed with "A Relay storage path escapes its root" and could not share leases with the other clients.
- Blueprint Lite shows what an agent writes without a reload. While a page is open, the server looks at the index and the board modules, the sketches and the comments of each project and tells the page of a change on one route, `/api/live`, as server-sent events or, for a page without them, as events since a cursor; a burst of writes is one event and the server's own saves are not told. The page reads the board module, the sketch or the comment threads again in place, keeping the camera, the selection and an open composer, and outlines for a few seconds what changed. A sketch with unsaved changes is never replaced: a notice, "The agent changed this board. Reload to see it.", offers the reload.
- Relay no longer lists, counts or wakes for a message that was already read when OneDrive delivers its inbox file late. An inbox file whose archive twin has identical bytes is hidden from `inbox`, `reminder` and the wake worker, and `read` removes it without returning it again; a twin with different bytes is still reported, and `read` ends with `ARCHIVE_COLLISION`.
- Relay wake leases and locks, which hold a process id, are kept in a folder local to the machine instead of the synced mind: `%LOCALAPPDATA%\hivem1nd\relay\<key>\wake\` on Windows and `$XDG_STATE_HOME` or `~/.local/state` elsewhere, keyed by the mind. A worker renews its lease at least every 5 seconds instead of on every poll, and writes a `worker: { state, heartbeatAt }` note into its own policy at most once a minute, which `relay wake status --machine <name>` reads for a binding of another machine. Lease and lock files left in the synced mind by earlier versions are ignored and removed by the worker of the same machine.
- `relay delivery --id <message-id>`, the MCP tool `delivery_status` and the store method `delivery` show a sender where its messages are: published, woken (the recipient's wake policy holds a delivery entry, where submitted means handed to the client and not read), read (the archive twin exists) and replied (a message answers it). They cover only messages the registered unit sent, at most 100 per call.
- Claude wake attach refuses a `--native-session-id` that is not the session running it, because the worker can only reach the pipe of that session: run from another Claude session, attach bound the caller instead of the target and left policies that woke the wrong chat.
- Blueprint Lite has a sketch mode, the Sketch tool of the viewer: a person draws screens on a board with rectangles, ellipses, lines, text, a freehand pen, pictures pasted from the clipboard or picked from a file, and arrows that join two screens, selects, moves, resizes and deletes them with the pointer or the keyboard, and undoes and redoes. The sketch is saved through a new route to `docs/flows/sketches/<board>.json` as Blueprint JSON v1, with the pictures in `docs/flows/assets/`, and the viewer draws its screens beside the board's own with a dashed edge, so an agent can read them and prototype. The one extension to v1 is that an arrow may end on a screen of the board module; the format is in the feature.
- A person can add a reference image to a Blueprint Lite sketch: the picture is saved in `docs/flows/assets/` and becomes a sketch screen, and with Send to agent on, the agent of the project is asked through Relay to recreate it as a screen of the board and to report in the comment thread of that screen.
- The comment box and the reply box of Blueprint Lite have a Send to agent checkbox, at the bottom edge of the field, with the unit it sends to and a dot that is solid when its wake is on and hollow when it is off, also told in text. The choice is kept in the browser and shared by every box, is on the first time, and is disabled with "No agent for this project" when the project has none; the main button reads "Comment and send" or "Comment" to match.
- The Blueprint Lite comment route accepts `send: true` on an add or a reply: the comment is saved as before, then sent to the agent of the project in a Relay message from `user` that quotes it, says where it is and asks for the answer in its thread of `docs/flows/comments/<board>.json`, which is the attachment. A message that fails is reported in the answer and in the page, and never loses the comment. `GET /api/agent/<project>` returns the unit and whether its wake is on.
- Void comments on a selection: releasing the mouse, or Shift after a keyboard selection, over words in a page opens a comment box under them with the quote, a field and a Send to agent choice that every box and the rail share and the browser remembers (on at first). Comments are saved in `<name>.comments.json` next to the document, in the format of the full Void app with the page key and offsets added to the anchor, so they find their words again after an edit; they show as highlights with a numbered margin button, take replies and are resolved. With the choice on, the server saves the comment and then sends it to the document's agent through the person channel of Relay with the comments file as the attachment, and a send that fails never loses the comment.
- Void live view: while a page is open the server watches the document and its comments file, and the page learns of a change from outside within about a second, updates in place without touching the text being typed, joins its own save with an agent's change to the same text where they do not touch, and marks the inserted and removed words of the latest outside change. Outside changes are logged in `<name>.versions.jsonl` with `"by": "outside"`, and a Changes view on the rail shows each page against its previous version.
- Void sends the person's own corrections to the document's agent: with Send to agent on, the saves are held and one Relay message lists the page texts changed with their text before and after 20 seconds after the last one, and a toolbar control shows and changes the same remembered setting. Turning it off drops the corrections waiting.
- Relay is the common pipeline of the kit, and every agent joins it. Install and update (`hivem1nd init`, `hivem1nd evolve`, so `/evolve`) run `relay diagnose` and then `relay configure` for each available client that has no `hivem1nd-relay` entry yet, pointing it at the mind's own copy of the CLI; a client that already has the entry keeps what a person edited, and only its Relay-owned hook entries are brought up to date in place. Each client gets one line, configured now, hooks brought up to date, already configured or not available, and the result lists the clients that need a restart. `relay diagnose` gains `configured` per client (`null` when its config cannot be read), and `--mind-path` for the Antigravity rules of one mind. Genesis writes the same steps in its text and enters and exits through `/relay`, writing `user/state/genesis.md`, so its one-per-mind block works. The packaged Windows app does not run it yet, since it has no `node` to point the clients at; the next `/evolve` does. `hivem1nd uninstall` and `/uninstall` run `relay unconfigure` for each client whose Relay entry runs the CLI copy inside the mind and report one line per client: removed, pointing elsewhere and kept, or no entry. An entry that runs another kit, and every foreign entry, stays.
- The entry of `/relay` joins every role to Relay: after registering, it attaches the wake with the default window of the kit when the client supports it, and when the session cannot be attached it runs `relay configure` for its own client only if that client has no Relay entry yet and tells the user to restart the client, otherwise it reports one blocked line with the reason. The rule is in `commands/relay.md` only, and the roles point to the entry.
- The Overseer, the Incubator and Genesis keep one session per unit, which makes the Overseer and Genesis one per mind. When their unit is already `in`, on this machine or on another, a new session no longer starts under a numbered unit: its Start stops with `Blocked: <unit> is in on <machine> since <date>.`, read from the state file, unless the user says the other session is closed, and then it takes the same unit over. The Executor, the Overlord and the Adjutant keep numbered units such as `executor-<project>-2` and `adjutant-2`. The numbering lived only in the role texts and in the unit step of `/relay`, so no code changed.
- The hand-off of `rules.md` reaches more roles: the Overseer may hand a task file to an Adjutant, an Overlord or an Executor, an Overlord to an Executor of its squad or its environment, and an Executor to a peer Executor, as before. The receiver takes the task only while it is in, within its own scope and permissions, and anything else in the message stays context. The Overseer delegates work that is not coordination to an Adjutant that is in, the Adjutant and the Overlord take the Overseer's hand-offs, and the Executor text matches.
- The Adjutant, a sixth role: it takes the user's requests and solves them end to end, such as documents and manuals, research, reports, writing and reviewing texts, analysis and the upkeep of the mind's own files when asked, so that the Overseer is left with coordination. It is an executive role whose unit is `adjutant`, then `adjutant-2` and so on, and it works with or without a repository. It coordinates no project, defines no scope, hands no task to an Executor and writes no product code; a change it would make to a product repository goes to that repository's Executor as a Relay request with no task file, which the Executor takes as context until the user confirms it. It may ask the Overseer for information and talk directly to Overlords and Executors after reading their state, tells the Overseer through Relay when its work touches a project, and delegates by the model table of `models.md`, verifying everything delegated first-hand. The Overseer delegates to it any work that is not coordination, by task file and Relay hand-off, when one is in. Every file in `roles/` already installs as a command, so installing and updating need no change.
- `relay read --thread-id <id>` ends with a usage error that points to `relay history`, instead of passing the thread to a store method that rejects it; `--thread-id` stays valid for `relay history` and `relay send`.
- `relay status --limit <count>` ends with a usage error instead of a store failure, because the status list takes only `--unit`.
- The Relay MCP `register` tool accepts `antigravity` as its `client`, so an Antigravity session can register through MCP like the other wake clients.
- `relay configure` falls back to the kit the running CLI belongs to when `--kit-path` is missing, and ends with a usage error when `--mind-path` is missing, instead of failing inside the config builder.
- Running `relay wake enable` or `attach` again no longer lets the wake point at a message it already submitted or could not confirm: the new policy keeps those delivery entries of the previous one beside its fresh window, handoff budget and wake count, and drops the ones that were not submitted, failed or in flight.
- Relay publishes a message, a session record or an event by linking the finished temporary file to its final name, so a file that appears at that name in the meantime ends the write with a collision instead of being replaced.
- The Claude wake sink checks the binding and the pointer text shape like the other clients before it writes to the session pipe: text that is not the Relay pointer for the unit is refused as `invalid_pointer`, and a binding whose machine name differs in case or whose session id passes 180 characters as `native_binding_mismatch`.
- `relay configure --client cursor` writes a 30 second timeout on the Cursor hooks, and raises it on hooks it already owns, because a stop hook that reads the mind through OneDrive measured 5 to 11 seconds on Windows and Cursor killed every one at the earlier 5.
- A malformed message no longer blocks a Relay inbox. `inbox` and `read` skip a message with invalid headers (an `attachments` header that is not JSON, a missing sender) or an oversized body and name it in `malformed`, and `history`, `threads` and `events` skip it too, so a wake worker no longer fails every poll on one bad file, fills its error budget and pauses the unit. `read` by id still fails for the id of the bad file.
- A Relay record that OneDrive has not finished syncing no longer ends a wake worker. The scans of `user/relay/sessions/` and of the wake policies skip a record that is malformed or busy (`EBUSY`, `EACCES`, `EPERM`, `EIO`, `UNKNOWN`, `EAGAIN`) and read it on the next poll, and a worker that meets one of those codes in a poll records the error against its budget and polls again.
- The Relay hook reminds a chat that changed unit instead of saying its session is not registered: a native session registered under more than one unit answers for the unit of its newest registration.
- A message stays context, never authorization, with one exception defined in `rules.md`: a hand-off, a Relay message to an Executor from a peer or a superior that points at a task file addressed to it. The Executor takes that task as its work, within its own scope and permissions.
- Relay hooks for Cursor and Codex on Windows read the hook payload as UTF-8 and pass it to node as UTF-8, and the hook strips a leading byte order mark, so the Cursor stop hook no longer fails with "Unexpected token" and accented text survives. Existing hooks pick this up with `relay configure --client cursor` or `--client codex`.
- A mind runs Relay setup on its own: an install or an update copies the kit's runtime dependencies into the mind's `node_modules`, resolved the way Node resolves them, so `relay configure`, `relay unconfigure` and `relay diagnose` work from the mind without a kit checkout. A dependency missing next to the kit is reported as a warning.
- Claude wake attach marks the session busy only when the Relay Stop hook is configured, since only that hook turns it idle again. Without the hooks the activity stays unknown, normal messages wake the session at once, and attach prints how to add the hooks.
- The Manager role is now called Overseer, the name the coordinator of the whole mind had before. The role, its skill, its unit `overseer` and its folder `user/overseer/` change name and nothing else. The `2.0.0-experimental.4` migration moves a mind's `user/manager/` folder, its `state/manager*.md` files and its root inbox to the new name and readdresses unread messages; a state file already named `overseer` is kept as a log entry, and logs and archived messages stay as written. An update removes the old skill as it removes any file the kit no longer ships.
- `hivem1nd view [--json] [--project <name>]`, the reader a host draws the mind from. It reads the states, tasks, inboxes, product documents and Relay records of a mind into one `hivem1nd-view-v1` document, defined in `files.md`, and writes nothing: the chats with their status and Relay reach, the squads with their roll-up, what waits on the person (the `Waiting on` lines of the root states, messages that ask for a reply, and the reviews a lead approved or that have no lead), the tasks, the unread inbox files, and the product documents with their requirements met per stage. A file it cannot read or parse becomes an entry of `issues` with its path and reason, the rest of the read is complete, and the exit code is non-zero only when the mind itself cannot be read. A file over 128 KB is not read, a folder over 2000 entries is read up to 2000, and a link or junction is never followed. `fixtures/view/mind` is a mind for it, with seven malformed task files modelled on the shapes that stopped another parser.
- The Overlord leads a squad as a mini overseer. Its scope is an environment, working exactly as before, or the chats of one repository, in which case it plans the request, splits it into tasks for its members, hands each one its task by the member's `job` when it has one, reviews each delivery first-hand and either approves it for the person with one line in the task's Report, `Approved for review by <unit> on <date>`, or sends it back to `open` with what is missing written in the Report, passes the person's decisions to its members and reports to the coordinator with the `User decisions` notes. The unit is `overlord-<environment>` or `overlord-<project>`. The state format gains two optional headers: `lead: <unit>`, the unit a member reports to, and `job:`, what the unit always does, such as `reader`, `archiver`, `builder`, `reviewer` or a short description. A squad is a lead plus every unit whose state names it, the unit name, its job and the model as the session records it live in the state so a host can create a chat by writing them, nothing ties a member to one tier, and a person's review of a task whose executor has a lead waits for the approval line, with no new status. A unit with no `lead` works as it did. An Executor with a lead takes its tasks from it, reports each delivery with a Relay message, copies the lead when the person messages it directly with something that changes the plan and keeps to its job. The Overseer talks to the lead, not to each member, unless the person addresses a member; `/plan` sends a task for such an executor to its lead, and `/qa` leaves the approval to the lead.
- The model table: `models.md` is a new record in `files.md` that says which model does which kind of work, at which effort, for every seat and every delegation. It has one row per kind of work and client with Work, Client, Model, Effort, Status (`active`, `paused` or `candidate`), Tested and Result, then a fallback order; a row changes only when a test changes it, a tool moves from `candidate` to `active` only after a real test (for another client, a Relay live trial), a tool that stops being available is `paused` and keeps its history, and prices stay out. The kit speaks in tiers, in a `delegation` knowledge category: plan, scope, product document and deep review at strong and max, seat work at strong and high and never delegated, builds from an approved plan at mid and high, read-only gathering at light and low, mechanical edits at mid and low; the seat verifies every delegated result and builders run their own tests. The Adapters section of Genesis maps the tiers to the model families of each client, and setup writes the first file from that mapping. The Executor takes the row of each piece, the Overseer names a row's model and effort when it briefs, a task may carry a `work` header, and `/qa` runs its subagents on the build row. The startup `check` prints one line for a row whose Client is neither a Relay wake adapter key nor `subagent`, naming its Work and the client; valid rows, a missing file and a file without a table stay silent, `--json` carries the findings under `mind.models`, and the measurement never fails the check.
- Product documents: every project has one, `projects/<project>/product.md`, a new record in `files.md` with a header (project, family, stage, updated, voice, board) and the sections Problem and audience, Value, Requirements per stage with an ID such as `APP-B-04` and an acceptance criterion each, Out of scope, Plans, Floors, Depends on, Open questions and Annexes. An annex, such as the architecture, holds the how in `projects/<project>/annexes/<name>.md`, or a repository path when it already lives there, and cites requirement IDs instead of restating them. The family product document holds the price table once and adds Rules, Product map, Stages and a pointer to the design direction. A brief Fact that changes a product document carries a `(product: <section>)` pointer and shrinks to one line, a task may list the requirement IDs it delivers in a `requirements` header, and one home per fact says which file owns each kind of fact.
- `product`, a knowledge module with the `product-requirements` protocol, run through `/protocol`: it gathers the brief, the scope and brainstorm records, the boards, the task Architecture sections and the voice specification, writes the product document with its requirements, out-of-scope list, open questions and annexes, and cross-checks it against the brief, the boards and the voice. `/brainstorm` stays the drafting tool, and there is no `/product` command.
- The startup `check` prints one line for a product document older than the newest brief Fact that carries a `product:` pointer, naming the project and the Fact date; a Fact without a pointer never triggers it. A project with a brief and no `product.md` is reported too: one line naming the project when the working directory resolves to it, and at the mind root one line with the count, none at zero. `--json` carries the list under `mind.product.missing`. A product document over 20 KB (`productBytes`) is listed with the other sizes, and `--json` carries the product document sizes and findings. The measurement never fails the check, and `/cleaner` lists product documents among what it measures.
- The seat of each project, its Executor, writes and keeps the project's product document: at the start of its session, when the project has a brief and none, it writes it from the records through the `product-requirements` protocol before other work, and afterwards it edits it in the turn a product decision is taken, sending the coordinator its `User decisions` note. The coordinator, the Overseer or the Overlord when the mind has none, reviews each product document against the user's decisions and approves it with the user, drafts one only for a project with no seat and owns the family product document. A decision taken with the coordinator reaches the seat as a brief Fact with its pointer and a `Product decision` Relay note, and the check reports the gap until the seat edits the document. The Incubator hands an accepted idea to the seat of its project, or to the coordinator when the project has none. A change to a product document that touches a shared contract sends one Relay note to each product listed in Depends on. `/plan` writes tasks that cite requirement IDs, and `/qa` reports the requirements met against the total per stage.
- The Relay host client is now `host`: `relay wake attach --client host`, the MCP `client` value and the wake adapter label use it, with no alias for the earlier id, and the Relay setup text, the files examples and the fixtures use generic host, machine and project names.
- An install or an update compares text without regard to line endings, because machines that share a mind may check the kit out with different ones. A kit file that already holds the same text under the other ending is left as it is and recorded as it is on disk, a recorded hash matches the file under either ending, and binary content is still compared byte for byte. A kit file that matches the record of another machine of the same mind (`machines/<host>.managed.json`) is managed and is updated or removed without a conflict, where it was reported as unowned or modified; a file that matches no record still asks for a choice, and a piece of the user's own in `roles/`, `features/`, `commands/` or `knowledge/` is still kept with a warning.
- `evolve` asks for conflict choices only in a terminal. Without one, it prints each unresolved conflict with its allowed choices and the `--conflict <path>=<choice>` syntax, never waits for an answer and exits with code 1.
- `/evolve` passes `--json` on every run and reads the conflicts from it. A mind that is not a Git checkout and is on a prerelease line (`user/VERSION` with a hyphen, such as `2.0.0-experimental.3`) no longer takes the published package as its base: the command uses a local clone of the kit repository on the branch of that line, fast-forwarded first, as `--kit-path`, and stops naming the clone it needs when the machine has none.
- The Antigravity allow rules that `relay configure --client antigravity` writes end in a token that refuses shell control characters (`;`, `&`, `|`, `<`, `>`, `(`, `)`, `$`, the backtick, `{`, `}` and line breaks) instead of a wildcard, so a chained, substituted or redirected command no longer passes when Antigravity matches the whole line; running `configure` again replaces the earlier rules, and `relay unconfigure --client antigravity` removes both forms.
- The Antigravity CLI wake lets a woken turn run to its result within 120 seconds (the controller bound moves to 125 seconds and the lease to 180 seconds, and the controller's retry-policy limits rise to 180 and 300 seconds), and `relay configure --client antigravity` adds a reversible allow rule in `~/.gemini/antigravity-cli/settings.json` for only the kit's `relay read` and `relay send` commands on one mind, which `relay unconfigure --client antigravity` removes.
- `/cleaner`, a feature that keeps a mind lean: it measures preferences, briefs, stale states, read messages, Relay history, evidence folders, machine files and the repos of the machine's paths, proposes every change in one list for a single yes, applies it with the replaced text kept in a log entry, and runs the check again to verify. The startup `check` prints one extra line, and adds the measurements to `--json`, when a threshold is crossed (preferences over 20 KB, a brief over 15 KB, a state left `in` for more than 3 days, more than 500 MB of files that are not records, a machine file over 15 KB, more than 1000 Relay history files); the walk over the files is capped and the measurement never fails the check.
- The files a machine installed move out of its machine file into `machines/<host>.managed.json`, the same path-to-hash map. Setup, attach and evolve read the old `## Managed Files` section while the JSON file does not exist, and the next write migrates it, so the machine file keeps only its header, Agents, Paths and Excluded. An `evidence` entry in Paths survives a new setup.
- Launch checklists digested into the packs: the security module gains `personal-data`, a protocol for consent, third-party scripts, deletion and export, marketing mail and the privacy, cookie, terms and refund pages, with a data subsection and a pre-launch item; the design pack gains honest choices (unticked consent, an equal decline, real urgency, the full price), checks for the on-screen keyboard, Back and reload, raw error text, image alternatives and font and image licences; the copy pack gains rules for hidden fees, reviews, compliance claims, footer notices and unsubscribe links.
- `/absorb` and every role keep orders tied to the moment (which tool, model, effort or quota to use now) out of preferences, and a new preference replaces the line it contradicts in place.
- Relay supports GitHub Copilot: `relay configure --client copilot` writes the user `mcp-config.json` that the Copilot CLI and VS Code Copilot both read, and a `copilot` wake adapter resumes an exact existing CLI session through its ACP server with the same bounds as the other adapters (exact session load, no session creation, permissions never approved, pointer-only text, environment allowlist, no replay of an uncertain dispatch). VS Code wake and Copilot hooks are not covered; see the Relay setup feature for the undocumented contracts that await a live trial.
- `device-reach`, a design protocol that checks the approved default on simulated low-end phones, computers, Linux, other browser engines and the product's own app against performance budgets, with evidence or a named gap per profile; `/qa` offers it, with the user's yes, for tasks in its scope.
- Same-day awareness: every seat sends the coordinator (the Overseer, or the environment's Overlord) one Relay note right after recording a user decision, correction or approval.
- Section tours: the design and copy packs teach each section on first opening with three or four key things and a More control that continues the tour.
- Executor, Incubator and Overlord fetch and fast-forward their repo before any work, not only at relay entry.
- Overseer, an executive role that manages the whole mind: it surveys every project, defines scope with the user one topic at a time, gates the work before it reaches the executors and keeps its memory in `user/overseer/`.
- `evolve` runs when started from a linked install inside the mind folder, and installs the roles, commands and features of the mind's `user/` folder when the kit and the mind are the same folder.
